2. PRE-FIX REPRODUCTION
-----------------------
Before this change the model-call diagnostic wrapper returned the provider's
final `result()` value unchanged:

    function observeModelCallFinalResult<T>(result, lifecycle): T {
      lifecycle.observer.observeFinalResult(...);
      lifecycle.emitCompleted();
      return result;   // <-- exact provider object, no call identity attached
    }

This was pinned by an existing regression test
(`attempt.model-diagnostic-events.test.ts`) that asserted `stream.result()`
was object-identical (`toBe`) to the provider message. The wrapper therefore
never propagated the runtime-allocated callId onto the AssistantMessage, and
the finalization path had no accepted-terminal call authority to forward.

When the additive field is introduced, that same `toBe` identity assertion
fails (observed post-change), which demonstrates the pre-fix behavior: the
exact AssistantMessage produced by the invocation did NOT carry the runtime
callId. The new authority tests below assert the desired `openclawCallId`
value; against the pre-fix wrapper they fail because the field is absent.

3. ROOT CAUSE
-------------
OpenClaw allocates the authoritative callId in `createModelLifecycle`
(`run/attempt.model-diagnostic-lifecycle.ts`) and emits it through
`model_call_started`/`model_call_ended` diagnostic events, but the callId was
never attached to the AssistantMessage returned by that same invocation.
Consequently finalization could only guess authority from the last observed
diagnostic hook, timing, or array position — all of which are unsafe for
Provenance.

4. CHOSEN callId OWNERSHIP MECHANISM
------------------------------------
Narrowest safe representation: an optional, runtime-owned field on the source
AssistantMessage type:

    openclawCallId?: string   (packages/llm-core/src/types.ts)

Why this cannot be supplied/forged by model content:
  - The field is stamped by OpenClaw's diagnostic lifecycle wrapper AFTER the
    provider returns, from the control-flow-local `lifecycle.eventBase.callId`.
  - The wrapper overwrites unconditionally (`{ ...result, openclawCallId }`),
    so any pre-existing value on the provider object is discarded.
  - Model text/content is never parsed to select the value; there is no code
    path that reads the value from content, timestamps, routing tier, provider,
    or prose.
  - `packages/llm-core` is OpenClaw's own monorepo package
    (`@openclaw/llm-core`), so this is an OpenClaw-owned metadata mechanism,
    analogous to the existing runtime-owned `turnId` and `diagnostics` fields.
  - No generated file was edited (`packages/ai/dist`, `packages/plugin-sdk/dist`,
    etc. are untouched).

6. EXACT PROPAGATION PATH
-------------------------
  runtime allocates callId
      (createModelLifecycle -> ctx.nextCallId(), eventBase.callId)
        |
  wrapStreamFnWithDiagnosticModelCallEvents -> observeModelCallFinalResult
      stamps openclawCallId = callId on the exact AssistantMessage returned
      by that invocation's stream.result()
        |
  agent-core agent loop (streamAssistantResponse.finalizeAssistantMessage)
      preserves openclawCallId through removeNonExecutableToolCalls /
      ensureToolTurnIdentity / withAssistantTurnTaint spreads, emits the
      accepted terminal message as message_end
        |
  subscribe layer noteLastAssistant -> state.lastAssistant (exact message)
        |
  handleAgentEnd -> runBeforeTerminalDelivery -> onBeforeTerminalDelivery
      event.lastAssistant carries openclawCallId
        |
  attempt-stream-prepare.ts onBeforeTerminalDelivery
      acceptedFinalCallId = resolveAcceptedFinalCallId(lastAssistant)
        |
  runAgentHarnessBeforeAgentFinalizeHook event.acceptedFinalCallId
        |
  hookRunner.runBeforeAgentFinalize receives acceptedFinalCallId
        |
  (agent_end, when lifecycle-safe)
      attempt-settle.ts computes acceptedFinalCallId from the settled
      terminal assistant -> state.acceptedFinalCallId
        |
      attempt-finalize.ts adds it to the agent_end event only on success.

9. FIRE-AND-FORGET INDEPENDENCE EVIDENCE
---------------------------------------
The authoritative association is synchronous and control-flow-local:

  - `createModelLifecycle` allocates `callId` synchronously before invoking the
    provider stream function.
  - `withOpenClawModelCallIdentity` is called directly by
    `observeModelCallFinalResult` when `stream.result()` resolves — it reads
    `lifecycle.eventBase.callId` from the same closed-over lifecycle object.
  - No state is shared with the async `model_call_started`/`model_call_ended`
    hook dispatch (`fireAndForgetBoundedHook`). Those hooks are observational;
    they cannot affect the stamped value.
  - Gate G test proves started/completed hook callId and the assistant
    `openclawCallId` agree, but agreement is a consequence of one source of
    truth, not a dependency on hook delivery ordering.

11. SECURITY / FORGERY ANALYSIS
-------------------------------
  - Model text/content cannot select the callId: the value is never parsed
    from content.
  - Provider payloads cannot forge it: the wrapper overwrites any
    pre-existing `openclawCallId` on the result object.
  - Timing/array position/hook ordering are not used as authority.
  - `resolveAcceptedFinalCallId` rejects toolUse/error/aborted/non-string
    values, so a predecessor tool call or a failed stream cannot leak its
    callId into acceptedFinalCallId.
  - agent_end only exposes acceptedFinalCallId on a successful terminal run.

11B. REVISION/SUPERSESSION LIFECYCLE CLOSURE (certification gap)
----------------------------------------------------------------
Exact new test (primary):
  src/agents/embedded-agent-runner/run.before-agent-finalize.test-support.ts
  -> "supersedes call_1 through the real revision loop and accepts call_2 as
     final authority" (executed via run.shared-integration.test.ts).

Actual call_1 -> revise -> call_2 trajectory exercised:
  1. Model call_1 produces a terminal-looking AssistantMessage carrying
     openclawCallId=call_1 (attempt 1 result.lastAssistant).
  2. The attempt boundary records beforeAgentFinalizeRevisionReason; the REAL
     run-loop calls the REAL resolveEmbeddedRunTerminal, which rejects this
     candidate and returns action="retry" with the revision continuation
     prompt. (The terminal-resolution test above also pins this branch
     directly, with openclawCallId=call_1 on the rejected candidate.)
  3. The REAL revision loop launches a second model invocation. Attempt 2's
     lastAssistant carries openclawCallId=call_2.
  4. Attempt 2 completes with no revision reason, so it is the accepted final
     execution authority.
  5. The test asserts exactly two attempts, acceptedCallIds ===
     ["call_1","call_2"], and acceptedCallIds[1] !== "call_1".

Why call_1 cannot remain final authority:
  - attempt 1 is marked with beforeAgentFinalizeRevisionReason; the real
    terminal-resolution path returns retry, so the orchestrator never returns
    attempt 1 as the final result.
  - The only attempt without a revision reason is attempt 2 (call_2), which is
    the one the loop accepts.
  - At the attempt boundary, the real onBeforeTerminalDelivery stamps and
    forwards call_1 only into the revision decision (attempt-stream-prepare
    test asserts acceptedFinalCallId=call_1 for the revise decision); the
    superseded candidate's delivery is suppressed.
  - The agent_end test asserts the completed revised execution forwards
    call_2, not the superseded call_1.

Final agent_end acceptedFinalCallId:
  - attempt-phase-lifecycle.test.ts:
    "forwards the revised execution's call_2, not the superseded call_1, to a
     successful agent_end event" -> event.acceptedFinalCallId === "call_2".

Historical/stale openclawCallId analysis:
  - attempt.model-diagnostic-call-authority.test.ts:
    "never lets a stale historical callId become the authority for a new
     invocation". A replayed/persisted assistant message carrying call_0 is
     passed through a NEW invocation; the runtime wrapper overwrites it with
     the freshly allocated call_2, so stale/historical identity never becomes
     the new authority.
  - The same guarantee is structural: resolveAcceptedFinalCallId reads only
    the openclawCallId stamped by the runtime wrapper on the exact message
    produced by the accepted terminal invocation; no code path reads a
    historical message field as acceptedFinalCallId.
